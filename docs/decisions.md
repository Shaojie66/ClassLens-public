# 技术决策记录

## 2026-11-02 项目启动

- **原生 Swift/SwiftUI，最低 macOS 26。** 要用系统的 SpeechAnalyzer、PDFKit、Voice Processing；不考虑 Electron/Tauri。
- **自己写，不 fork Nomi。** 核心差异是“课件阅读 + 划词提问”，Nomi 没有，而且它依赖 Rust + MLX 后端，构建链太重。只借鉴设计。
- **识别引擎做成协议，暂不定死。** Nomi 用了本地 Qwen3-ASR 1.7B，没有用 SpeechAnalyzer。M1 用同一段真实上课录音对比两者的术语准确率再定。
- **课件术语表是全局上下文**（参考 LectureFlow）：同时用于识别（contextualStrings）、翻译用词和答题。
- **提问识别分三层**（参考 Nomi）：规则粗筛 → 过滤口头禅 → 有候选句才调 LLM，且延迟约 3 秒，让老师把话说完、排除自问自答。
- **以下默认值未经用户逐项确认，按推荐值执行，可随时改：**
  - AI：DeepSeek，V4.1-Flash 负责翻译和判断问句，V4-Pro 负责答题；预留 Claude/OpenAI 接口
  - 音源：MVP 只做麦克风
  - PPT：PowerPoint 转 PDF，Keynote 兜底
  - 答题：检测到提问自动生成，过滤反问句
- **签名**：用本机 Apple Development 证书（Team M9SMPTK6FN），这样重新编译后麦克风权限不会被重置。不开 App Sandbox（后续要通过 Apple Events 调用 PowerPoint）。

## 2026-11-02 识别引擎对比（M1）

样本：用户提供的一节真实课程录音（约 112 分钟，统计假设检验，老师有口音，远场录音），截取第 10、55、100 分钟起各 3 分钟。没有人工字幕，靠四个引擎互相对照，再统计术语命中次数。脚本：`Bench/speechanalyzer.swift`、`Bench/local_asr.py`。

| 引擎 | 速度 | 术语表现 | 结论 |
|---|---|---|---|
| Apple SpeechAnalyzer | 18–29× 实时 | 0 次 null hypothesis；theta 被听成 "Tata"，H0 被听成 "page 0"，整句常常读不通 | 淘汰 |
| Qwen3-ASR 1.7B（8-bit MLX） | 13–22× 实时 | null hypothesis 8 次，theta、H zero/H null、t-test、standard deviation 全对 | **主引擎** |
| Parakeet TDT 0.6B v3 | 21–94× 实时 | 接近 Qwen3，但把 theta 写成 "teta"，有几处听错 | 备用（轻量、快） |
| Whisper large-v3-turbo | 5–26× 实时 | 准确率接近，但第一段末尾陷入幻觉循环（"Let's see." 重复 20 多次，超出音频时长） | 淘汰 |

- **决定：主引擎用 Qwen3-ASR 1.7B，Parakeet 作备用**，都通过 Swift 包 mlx-audio-swift（MIT）接入，App 不带 Python。
- Qwen3-ASR 不是原生流式模型。实时字幕的做法：按停顿切句，每句说完立即识别；说话过程中每隔约 1 秒对当前句重新识别一次，作为临时字幕。
- 还没验证：(1) 在 App 里实时运行的延迟和内存占用；(2) Qwen3-ASR 注入课件术语后能否进一步纠错。
- 这只有一节课的样本，换一个老师结论可能不同，Parakeet 作为备用保留。

## 2026-11-02 M1 实时转录落地

- **依赖版本锁定**：mlx-audio-swift 0.1.4 + mlx-swift 0.31.4。0.1.5 及以后经 mlx-swift-lm 依赖 mlx-swift ≥ 0.32.3，而 mlx-swift ≥ 0.31.5 要求 Swift 6.3，本机 Xcode 26.3 只带 6.2.4。升级 Xcode 后可以解除锁定。
- **切句**：能量阈值 + 自适应噪声底；停顿 0.6 s 判定为一句结束，单句上限 15 s。这位老师很少停顿超过 0.6 s，约 1/8 的句子是被上限切开的。
- **调度**：同一时间只跑一个识别任务；正式字幕优先、按顺序处理；临时字幕只保留最新一个，引擎慢的时候直接丢弃旧的，不积压。
- **MLX 缓存上限设为 256 MB**：不设的话，每次输入长度不同，缓存会一直涨。2 分钟回放内存就涨到 4.1 GB，在内存吃紧时还会让单次识别卡住 36 秒。
- **验收结果**（Release 构建，从第 600 秒起 1 倍速回放 600 秒，同时 ollama qwen3:8b 占着 GPU，系统交换区几乎用满）：
  - 临时字幕延迟 p95 0.81 s（目标 ≤ 1.5 s）
  - 停顿后出正式字幕 p95 1.95 s（目标 ≤ 2 s，余量很小）
  - 长句切分后出正式字幕 p95 1.77 s
  - 内存峰值 3.48 GB，识别速度 15× 实时，无重复循环，无错误
- **遗留问题**：
  - 系统内存或 GPU 吃紧时，仍可能偶发单次识别卡顿数秒，限制缓存后的一次 2 分钟回放里出现过一次（正式字幕最长延迟 11.9 s）。卡顿后会在几秒内追上进度，但追上之前字幕会滞后。可选的缓解办法：换 4-bit 模型降低内存（需要先测准确率）。
  - 麦克风实录和教室麦克风模式只做了编译，还没实际验证，需要用户点录音按钮并授予麦克风权限。
  - 术语表挪到 M4，和课件阅读器一起做。

## 2026-11-02 M2 逐句翻译

- **翻译单位是正式字幕**，附带前 3 条中英文作上下文；只翻译正式字幕，不翻译临时字幕（避免中文来回跳、浪费调用）。
- **模型**：`deepseek-flash`（V4.1-Flash），非思考模式（`thinking: disabled`），temperature 0.3，最多 3 个请求并发；限流、服务器出错、超时各重试 1 次，key 无效和余额不足不重试。
- **存盘**：transcript.jsonl 只追加，英文先写，翻译回来再补一行，读取时以最后一行为准。
- **验收**（Release，从第 600 秒起 1 倍速回放 180 秒，真实调用 DeepSeek）：翻译延迟 p50 1.00 s / p95 1.14 s（目标 ≤ 2.5 s），19/19 条翻译成功，0 错误；识别指标不受影响（正式字幕 p95 1.31 s，内存 3.3 GB）。回放时长比规范的 10 分钟短，但字幕密度与之前 10 分钟那次一致。
- **已知问题**：识别错误会被照搬进译文（null hypothesis 被识别成 "no hypotheses"，译成“我没有假设”；"H nil" 被译成“H空”），留给 M4 的课件术语表解决，不在提示词里硬编码某一门课的词；断句处偶尔衔接不上。
- **费用估算**：一节 2 小时的课约 1100 次请求，按峰时价约 0.2 美元。

## 2026-11-02 M3 提问识别与自动答题

- **三层过滤**：规则粗筛（问号或疑问词开头，去掉 "right?" 等口头禅，清单改编自 Nomi）→ 攒批 → `deepseek-flash` 用 JSON 输出判断类型（directed / rhetorical / check-in / logistics），只回答 directed。
- **攒批时机**：疑问句出现后，等老师再说 2 条字幕，或 8 秒没有新字幕，或这一批已经开了 20 秒，再一起判断；连续追问合并成一条。
- **判断依据写进提示词**：每行附上说完后的停顿时长；超时触发时会告诉模型“之后至少 8 秒没人说话”。算 directed 必须有证据：停顿 ≥ 2 秒、后面跟着远处学生回答被识别成的短句或乱句、老师重复提问或邀请回答、老师回应答案；没有证据就算 rhetorical。
- **答题**：`deepseek-v4-pro`，非思考模式，流式输出；上下文是问题之前约 40 条字幕。格式为“答案 / 可以这样回答（英文一句）/ 解释”，不超过 200 字。识别漏掉的问题可以在字幕上右键手动触发。
- **评估方法**：从同一节课取三段 10 分钟转录（第 600、3000、5400 秒起），人工标注出 6 个向全班的提问；第 3000 和 5400 秒那两段在调提示词之前就标注好，调参时不看，作为留出集。打分脚本：`Bench/score_questions.py`。
  - 改提示词前：召回 6/6，误报 5 个（dev 2、留出集 3）
  - 改提示词后：召回 6/6，误报 2 个（dev 1、留出集 1）；dev 重跑一次结果相同
  - 剩下的误报都是边界情况：问完停顿 1.3–1.6 秒，或者识别得一塌糊涂的句子
- **局限**：只有一位老师、一节课、6 个正样本，数字只能说明方向。换一位更爱提问、或者停顿习惯不同的老师，阈值可能需要调整。
- **修复：长句期间被误判为“没人说话”**。疑问句后面如果跟着一句很长的话，它在说完之前一直只是临时字幕，8 秒内没有新的正式字幕，超时就触发了，模型还被告知“至少 8 秒没人说话”。改为临时字幕也算老师在说话，延后判断（受 20 秒上限约束）。这个误报只在实时运行时出现，离线评估走不到超时路径，所以测不出来。
- **实时验收**（Release，第 600 秒起 1 倍速 600 秒，修复后）：真问题 3/3，误报 1 个（3:43，边界情况）；答案开始出字 p95 1.38 s，完整答案 p95 4.96 s。**识别出问题 p95 12.9 s，比 12 s 的验收线多 0.9 s**，原因是等老师把长句说完；2026-11-02 用户决定把验收线放宽到 15 s，因为这段等待正是去掉误报的代价；按新验收线达标。
- **识别延迟超标，原因未确定**：最近两次完整回放的正式字幕 p95 为 4.15 s 和 3.45 s，超出 2 s 的验收线。当时 ollama 正在 GPU 上被调用（qwen3-embedding:8b），还有 iOS 模拟器和其他项目的 xcodebuild 在跑。同样环境下只做识别的 2 分钟回放达标（p95 1.46 s），M3 第一次完整回放（负载较低时）也达标（p95 1.17 s），所以倾向于是资源争抢，但没有证实。
- **修复**：启动参数原先挂在主窗口的 `.task` 上，主窗口没出现时（从命令行启动时遇到过，具体原因没查明，不是窗口状态恢复）无界面验证会一直空转。改为在 `applicationDidFinishLaunching` 里处理。

## 2026-11-02 M4 课件阅读、划词提问、术语表

- **课件**：PDFKit 阅读器，支持 ⌘O 和拖入文件；选中文字后右键，有“让 AI 解释这段 / 翻译这段 / 就这段提问…”三项，答案进问答页并记下页码；自动答题时，把学生当时打开的那页课件一起作为上下文。
- **术语表**：打开课件时，用 `deepseek-flash` 从全文抽出最多 80 个“英文术语 → 中文译名”，按文件 SHA-256 缓存。用在三处：识别的 context（最多 60 个，长的优先，去掉单个拉丁字母）、翻译时统一用词、答题时作参考。
- **发现：识别模型会复述上下文**。第一次实验里，0.8 秒的咳嗽声被识别成了整串 “Technical terms in this lecture: …”，凭空多出 rejection region、degrees of freedom 等老师没讲过的词。两层防护：不到 2 秒的片段不给上下文；识别结果里出现上下文的开头语，或连续 4 个以上用逗号隔开的术语，就去掉上下文重识别，并计入 `contextEchoes`。加上防护后两段共 20 分钟回放，复述次数为 0。
- **效果**（自制 6 页“假设检验”样例课件，第 600 秒和第 5400 秒起各 10 分钟；切句结果完全相同，唯一的差别是有没有术语表）：词级别有改动的片段分别是 28/94 和 38/115。逐条人工判断：明显变好约 25 处（note → null、no response → null hypothesis、p zero → t zero、solution → statistic/distribution、perimeter → parameter 等），变差 3–4 处，另有 2 处疑似被术语表带偏（open source → confidence intervals、how successful → hypothesis testing），原文是什么无法确认。
- **局限**：样例课件是我自己做的，覆盖的正好是这节课讲到的术语，测出的效果会偏乐观。
- **用真实课件复测**（用户提供的 SCEM Week 7 "Introduction to Statistical Inference"，60 页，确认与录音是同一节课；课件不进仓库）：抽出 76 个术语。三段各 10 分钟，其中第 3000 秒那段之前从没用来测过术语表。
  - 复述上下文：被拦下 2 次（都在第 3000 秒那段），重识别后字幕中为 0。防护在真实课件下会被触发，不能去掉。
  - 明显变好的例子：opponents / another horse / open box / no response / responses → null hypothesis；note … tendency → null … alternative；compensator ×2 → confidence interval；lose → reject；perimeter / product → parameter；instagram → instrument；decibel → dataset；citizen / physical power → statistical power；platform or Python → R Python（老师应是说 R or Python）。
  - 一处看似“凭空多出 20 多个词”的改动经核查不是编造：用不带上下文的 Parakeet 识别同一段音频，也听到了这段话，是不带术语表时 Qwen3 漏识别了。
  - 仍有问题：how successful → hypothesis testing、open source → testable principles 这类“往课件词上靠”的改动依旧存在，原文无法确认；另有几处变差（limit → mean time，this estimation → disclamation）。MSc students（被听成 MC / NC / NSE / massive students）没纠正，MSc 不是术语，不在术语表里。typhoon errors 在不到 2 秒的短片段里，按设计不给上下文，也没纠正。
  - 结论：真实课件下收益明显大于代价，保留术语表上下文，默认开启。"no hypotheses" 那句和短片段里的 "typhoon errors" 仍然没纠正（短片段按设计不给上下文）。
- **翻译**：带课件的 150 秒实时回放中，原假设、备择假设、p 值等译法前后统一；翻译 p95 1.2 s，识别正式字幕 p95 1.05 s。
- **界面修复**：右侧“字幕 / 问答”切换按钮在内容较少时会被垂直居中（M3 引入，当时没截图检查，所以没发现），现已固定在顶部。
- **未验证**：右键菜单、拖入文件、自定义提问输入框都需要点击操作，按规则要交给 Codex 执行，所以没有实际点过；划词提问走的是和 M3 相同的流式答题链路，只是换了提示词。

## 2026-11-02 M5 PPT 导入

- **使用场景**（用户 2026-11-02 说明）：课前先导入 PPT，老师再开讲；学生通常不跟着翻页。已写进 CLAUDE.md。
- **转换方式**：用 `osascript` 让 PowerPoint 导出 PDF，PowerPoint 不可用时改用 Keynote。导入时自动转换，结果按源文件 SHA-256 缓存，之后统一按 PDF 处理。第一次转换时，系统会请用户允许 ClassLens 控制该应用。
- **安全**：只认按文件名找到的、刚打开的那份演示文稿，绝不用“当前演示文稿”，避免误存、误关学生自己开着的文件。出错时只关掉自己打开的文件；应用原本没开的才退出，原本开着的不动。
- **问题 1：冷启动与查找演示文稿**。第一版取“当前演示文稿”，冷启动时 PowerPoint 还没就绪，取不到。改成按文件名逐个查找、最多等 30 秒；PowerPoint 的脚本不支持 `whose` 筛选（报 -1750），所以用循环。关闭时也按文件名重新查找。Keynote 改为先启动并等待就绪。复测：PowerPoint 冷启动 6 秒，转完自动退出，没有残留打开的文件；Keynote 冷启动 8 秒。
- **测试方法的坑**：一开始为了绕过缓存，往 PPTX 末尾追加了一个字节，这会损坏 zip，PowerPoint 于是进入“修复”模式并弹出对话框，导致好几次转换失败、超时。改用 `Bench/make_fixture_pptx.py <输出> <标签>` 生成内容不同的合法文件。另外，PowerPoint 关掉演示文稿后会保留隐藏窗口，窗口列表不能用来判断文件有没有关掉，要以脚本里 PowerPoint 自己报告的演示文稿列表为准（`CLASSLENS_TRACE=1` 时打印）。
- **问题 2：PowerPoint 导出的 PDF 有“ti”连字乱码**（Calibri 字体：Statistic → Sta:s:c，critical → criTcal）。`LigatureRepair` 把“字母:字母”和“小写 T 小写”换回 ti，但只有修复后的词出现在系统词典 `/usr/share/dict/words` 或同一份课件的其他位置时才替换。页面文字、术语抽取和划词提问都经过修复。阅读器里显示的仍是 PDF 原样，因为显示用的是字形，本来就不乱。
- **耗时**：PowerPoint 已在运行时 4–10 秒，冷启动 6 秒；Keynote 冷启动 8 秒；第一次（含权限弹窗）约 2 分钟。
- **未验证**：.ppt（旧二进制格式）和 .key 文件没有测试样本。
- **顺带修复 M1 的崩溃 bug**：切句器在 15 秒上限处强制切分时，如果切点落在停顿里，会把整段安静帧的计数带进更短的后半段，接下来判断停顿时下标变成负数，App 直接崩溃（实际上课时就是录音中途闪退）。单元测试偶尔暴露过一次。改为按后半段自己的音量数据重新计算末尾的安静帧；新增的回归测试在修复前的代码上必定崩溃，修复后通过。

## 2026-11-02 自动跟随老师讲到的页

- **方法**：`SlideTracker`。先把动画逐步出现的连续页面合并成一张幻灯片（前一页 80% 以上的词在下一页里也有，就算同一张；真实课件 60 页合成 26 张），显示和答题都用这张幻灯片的最后一页（动画全部展开）。每来一条正式字幕，拿最近 75 秒的转录和每张幻灯片做 TF-IDF 余弦相似度，再用 HMM 前向滤波：主要停在当前张，往后 1–3 张概率较小，往回 1 张更小，任意跳转合计 0.0005。符号统一写法（数学斜体 𝐻0 → H0，"H zero" → h0，θ → theta，type one → type1）。换页需要连续两次概率 ≥ 0.5。
- **评估**：整节课转录 + 我读转录对照课件文字标注的 34 个时间点（排除 R 现场演示和课间休息）。标注和算法部分共用“说的话像哪页”这一信号，结果偏乐观。前半节（18 点）调参，后半节（16 点）留出。
  - 调参前：dev 完全对 8/18、正负一张以内 16/18；test 7/16、12/16；整节课换页 72 次（实际约 25 次）。
  - 调参后（默认值）：dev 8/18、17/18；test 6/16、13/16；换页 44 次。调参主要换来稳定，准确度没有提升；各种参数组合下“完全对”都在一半左右，主要错法是慢一张。
  - 结论：约 4 成完全对上，8 成在正负一张以内。

## 2026-11-03 收紧提问识别、课间暂停、总结里的推断数字（用户要求）

- **起因**：核对 Week 7 时发现，18 个识别出的提问里有 10 个是误判（约 0.9 个 / 10 分钟，刚好压在原来“每 10 分钟 ≤ 1 个”的验收线上），其中 2 个发生在课间；AI 总结把转写里的 "fifteen" 推断成 50，直接写成了确定的结论，没有标出来。

- **整节课标注的局限**：只核对了程序识别出来的那些句子，没有通读全文去找漏掉的提问，所以召回率只能按已知的真提问来算。看过基线结果后改了两处标注，都写在 labels.json 里：1188 s 那句老师在同一行就自己答了，从“真提问”改成“拿不准”；5398 s（问 p 值偏大还是偏小，停了 2.5 s）加为“拿不准”。
- **调参范围**：只看 3000 s 以前。旧的两段留出集也是从这节课切出来的，都在 3000 s 以后。
- **基线**（改动前的 Release，评估模式）：整节课误报 12 个（1.07 个 / 10 分钟）。真提问后面都有停顿以外的证据：学生零碎的回答（"One."、"To each side."）、老师复述，或者老师说 "let's go"、给提示。误报大多只有停顿，而停顿里往往是笑声或 "Okay"。其余误报是识别错误：陈述句被加了问号（"Which we don't know yet."），或者句子乱码。
- **改动 1：判定提问**
  - 模型要给出证据类型 `signal`：`student-answer`、`teacher-repeats`、`invites-answer`、`reacts-to-answer` 或 `silence-only`。只有停顿时（`silence-only`），程序一律不算提问。
  - 新增两类：`statement`（识别把陈述句或半句话标成了问句）和 `unclear`（太乱，看不出在问什么）。
  - 课间相关的提问（投票要不要休息）归到 `logistics`。
  - **代价**：如果学生在远处回答、麦克风没收到，老师也只是沉默等待，这样的提问会漏掉。
- **改动 2：课间暂停**（`BreakWatcher`）
  - 课间的转写是一串紧挨着的 13–15 s 长句，是教室噪声被识别成了像讲课的乱话，所以看内容和说话密度都分不出课间，只能靠老师自己说的话。
  - **开始**：听到宣布休息（"break now"、"three minute break"、"let's take a break"）。"after the break" 这类说以后的不算。
  - **结束**：开始 60 s 以后，听到回来的话（"All right, back"、"welcome back"、"let's go/continue"）。
  - **没听到回来的话时**：自动恢复的时间是宣布时长的两倍，至少 8 分钟、最多 20 分钟；没说时长就是 15 分钟。
  - 课间开始时，还没检查的那批候选问句直接丢掉。
  - 提问栏显示“课间休息，暂停识别提问”，可以手动点“继续识别”。
  - 时间一律用转写时间，所以回放和评估跟上课时一样。
  - 规则是照着这节课唯一的一次课间写的，所以这里的结果不能算留出验证。
- **结果**（Release，评估模式）：

  | 范围 | 召回 | 误报 |
  |---|---|---|
  | 调参段 | 2/2 | 4 → 0 |

  | 整节课（跑了两次） | 6/6 | 两次都是 0（0 个 / 10 分钟） |

  - 提示词：凡是推断出来的数字（听错后改正的、自己算出来的、在几种说法里挑了一个的、按上下文补上的）一律写进“待核对”，正文不能写成定论。前后说法不一致时，两个都列出来。“待核对”只列真正需要核对的。

## 2026-11-16 用学校字幕给识别引擎打分（FOAI 9 月 25 日，Colab）

- **数据**：本来打算用 Blackboard 上学校录的音频，再由用户人工校对一小段作标准答案。实际情况是 Re/Play（Mediasite）只开放字幕下载；直接请求视频流，命令行返回 403、浏览器里返回 400，所以没拿到学校的音频（试到这一步就停了，没再继续绕）。最后由用户决定，拿学校的 **自动生成** 字幕（`English [Auto-Generated]`）当标准答案；音频用用户自己在 9 月 25 日录的同一节课（CourseDude，远场，55 分钟）。
- **对齐**：两份录音里各只出现一次的 5 词短语共 4046 个，用它们求出时间偏移：43.50 s。每 300 s 分段检查一次，偏移都在 ±0.2 s 内，没有漂移。字幕平移到用户录音的时间轴上，每约 300 s 切一个窗口，切点放在字幕行的起点，一共 10 个窗口、6488 个参考词。
- **脚本**（都放在 `Bench/`）：
  - `captions_to_gold.py`：从字幕生成标准答案；
  - `local_asr.py --jsonl`：整节转写，在停顿处切成 ≤ 15 s 的块；
  - `colab_asr.py`：在 Colab L4 上跑大模型；
  - `score_asr.py`：打分（lowercase、去标点、数字转成英文单词、去掉 um/uh 等填充词；WER 按所有窗口的错误总数除以参考词总数计算）；
  - `sample_windows.py`：给以后人工校对用的抽窗口脚本，这次没用到。
  - 测试在 `Bench/tests/`。
  - 字幕、音频和转写结果都放在 `Bench/data/asr_eval/`，不进仓库。

| 引擎 | WER（对学校字幕） | 速度 |
|---|---|---|
| Parakeet TDT 0.6B（本机） | 11.5% | 73× |
| App 实际输出（Release，`--asr-only --replay-speed 0`，Qwen3 8-bit） | 11.9% | 19×，峰值内存 3.7 GB，contextEchoes 0 |
| Qwen3-ASR 1.7B bf16（Colab L4） | 12.2% | 19× |
| Canary-Qwen-2.5B（Colab L4） | 12.3% | 13×，有一处长段幻觉（"no no …" 256 次） |
| Qwen3-ASR 1.7B 8-bit（本机，裸跑） | 12.4% | 17× |
| Qwen3-ASR 1.7B 4-bit（本机） | 12.4% | 36× |
| Whisper large-v3（Colab L4） | 13.0% | 21× |
| Whisper large-v3-turbo（本机） | 13.7% | 26×，有幻觉（"you" 连续 28 次） |

- **这个分数有多可信**：几个引擎互相之间只差 4.5–7%（Qwen3 bf16 对 8-bit 4.5%，对 Parakeet 6.9%），但每个引擎和字幕都差 12% 左右，而且都多出约 400 个插入词。原因是字幕本身是机器识别的，又只录到老师的领夹麦；用户的远场录音里还录进了学生说话和老师的口头重复。所以这次的 WER 主要量的是「和学校 ASR 的差距」，**引擎之间不到 1 个百分点的差别分不出来**。
- **结论**：
  1. 4-bit 和 8-bit 在这个标准答案下分不出高下（都是 12.4%），4-bit 速度约是 8-bit 的 2 倍，可以作为降内存的候选；但要真改，得先在有人工标准答案的数据上确认。
  2. 量化损失很小：bf16 12.2% 对 8-bit 12.4%。
  3. App 的切句加上下文流程不比裸跑引擎差（11.9% 对 12.4%）。
  4. 换一位老师（FOAI）后，Qwen3 和 Parakeet 仍然是第一梯队，Whisper 两个版本都更差，还会出幻觉，这和 M1 的结论一致。
  5. 主引擎不换。
- **Colab 用量**：L4，一共消耗 0.51 个算力单位（199.98 → 199.47）。踩过的坑：faster-whisper 需要先手动加载 CUDA 12 的库；pip 升级 huggingface_hub 后要重启 kernel；Canary 需要升级 torchao。
- **遗留**：这次得不到真 WER。要出真 WER，仍然需要人工校对过的标准答案（用 `sample_windows.py` 抽窗口）。另外，App 回放在用户的 ClassLens 会话记录里留下了一条会话 `C5B019D9…`。

## 2026-11-16 接入 Claude API，与 DeepSeek 并存可切换（用户决定）

- **决定**：新增 Claude 作为第二个 AI 服务商，在设置里切换，DeepSeek 保留且仍是默认。用户原话：「我想用 claude 的 api」「并存可切换」。
- **理由**：提问识别的提示词和 M3 评估集都是照 DeepSeek 调的，Claude 的结果和延迟都还没测过；并存可以逐项对比，不达标时随时切回。
- **做法**：
  - `AnthropicClient` 实现 `LLMClient`，直接用 URLSession 调 `POST https://api.anthropic.com/v1/messages`（`anthropic-version: 2026-10-21`）。Anthropic 没有官方 Swift SDK，不新增依赖。
  - 模型：答题和课后总结用 `claude-opus-5-5`，翻译、判问句、跟页、术语抽取用 `claude-haiku-5-5`。
  - 与 OpenAI 格式的差别：`system` 是顶层字段；不发 `temperature`（这两个模型非默认采样参数会报 400）；Opus 5.5 不能关思考，用 `output_config.effort: "low"` 控制延迟；Haiku 5.5 发 `thinking: {type: "disabled"}`；开着思考时 `max_tokens` 要给思考留余量；需要 JSON 时靠提示词，并去掉回复里的代码围栏。
  - Opus 5.5 的请求带 `fallbacks: "default"`（beta `server-side-fallback-2026-07-01`），安全分类器拒答时由服务端换模型重跑；仍然拒答（`stop_reason: "refusal"`）按错误处理。
  - 密钥存钥匙串，账户名 `anthropic`；当前选中的服务商存 UserDefaults（`llmProvider`），只存名字。
  - 错误类型从 `OpenAICompatibleClient.Failure` 提成两家共用的 `LLMFailure`。
- **还没验证**：Claude 下的 M2 翻译延迟、M3 提问识别评估和答题延迟都没有跑过；在跑过之前，各验收线的结论只对 DeepSeek 成立。

## 2026-11-16 接入 OpenAI 作为第三个服务商（用户决定）

- **决定**：设置里的服务商加上 OpenAI，和 DeepSeek、Claude 并列可切换。用户原话：「把 Claude 、openai接入也合并到公开仓库」。
- **做法**：沿用 `OpenAICompatibleClient`，地址 `https://api.openai.com/v1/chat/completions`，钥匙串账户 `openai`。
  - 模型（[模型页](https://developers.openai.com/api/docs/models)，2026-11-16 查）：翻译、判问句、跟页、术语抽取用 `gpt-6-luna`（最便宜，$0.10 / $0.50 每百万 token，`reasoning_effort: none`）；答题和课后总结用 `gpt-6.1-sol`（$2 / $10，最低只能 `low`）。这是按价格和用途选的默认值，没有和 DeepSeek、Claude 对比过效果。
  - 这两个都是推理模型。Chat Completions 文档写明 `max_tokens` 已弃用、和推理模型不兼容，所以对它们改发 `max_completion_tokens`；开着推理时多给 4096 留给推理。文档说推理模型的参数支持会不同，`temperature` 一律不发，用默认值。
  - OpenAI 余额不足时也返回 429（错误码 `insufficient_quota`），这种情况按“余额不足”报错，不当成限流去重试。
- **还没验证**：没有 OpenAI key，没有做过真实调用；各验收线同样没在 OpenAI 下跑过。
